# 空间造物局 软件需求说明书

项目作品名为「角落计划」，选题为主题二「空间造物局——交互式空间布置与方案编辑 App」。项目按单人方案组织，工作范围为应用设计、实现、集成、测试和演示。实际个人贡献以本人 GitHub 提交为依据。

## 使用情境与范围

宿舍和校内社团在摆放物品前，需要比较不同布局，检查物件是否离开室内边界或压住其他物件，并在活动前取回曾经保存的方案。应用提供二维顶视编辑和同机离线保存。尺寸为方案坐标，用于对比布局方案，现场实施前另行测量。

| 编号 | 需求和约束 | 验收 |
| --- | --- | --- |
| R1 | 两种独立底图，宿舍 480 × 360、社团展位 420 × 320。标明入口与场地结构。至少 6 类物件，允许同类多实例。 | 分别进入两种底图，确认不同边界和入口图形；依次添加床、书桌、收纳柜、椅子、展台、展板。 |
| R2 | 点按选中，拖动预览并在松手时形成一次编辑。提供 15° 旋转、0.1 倍缩放和删除，缩放范围 0.5～1.8。选中物件可通过工具条操作。 | 检查拖动、旋转、缩放后几何确实改变，删除后对象消失。 |
| R3 | 每份当前编辑会话维护最多 60 步快照，撤销和重做互逆，撤销后新动作清除重做序列。 | 移动、删除后撤销与重做，新建编辑后检查重做按钮。 |
| R4 | 越界或覆盖较小物件实际面积 20% 及以上时标红并给出说明。只接触边缘允许通过。允许保存带提示的草案。 | 注入边缘相切、越界、明显重叠、旋转后的邻接和阈值边界样例。 |
| R5 | 方案名去首尾空白后为 1～24 字符，方案以稳定 ID 标识，同名可通过缩略图和场景区分。至少保存 3 份，容量上限 30。列表含名称、底图、物件数和图形预览。 | 保存三份命名方案，轮流打开，比较各自布局。更新已有 ID 后容量不增加。 |
| R6 | Preferences 采用单键版本化方案集，保存须等待 flush。退出进程后恢复方案列表，重新打开后可继续编辑。解码失败阻止覆盖并提示。 | 对比进程终止前后同一方案，检查物件位置、大小、角度，继续变换并更新保存。 |
| R7 | 未保存编辑切换页面时确认；保存失败保留当前编辑，用户可以重试。空列表提供新建入口。 | 输入空名称并提交；验证取消离开；Mock 提交失败后重试。 |

## 模块与数据

- Index 和 PlanView 负责工作台、底图选择、物件工具、方案列表及画布预览。触摸通过平移和缩放映射到布局坐标。
- LayoutHistory 维护独立快照，apply 提交有效新状态，undo / redo 返回可选快照。LayoutRules 接收 Plan，计算命中、物件交集和边界结果。
- Plan 持有 ID、名称、底图编号和有序 PlacedItem 列表。PlacedItem 持有 ID、物件种类、中心坐标、缩放和旋转角。顺序表示前后叠放关系。
- PlanRepository 面向 TextStore（read、write），负责读取解码与持久化方案快照。PreferencesStore 把 TextStore 映射到端侧 Preferences，单次写入等待 flush。
- 核心测试使用内存 Mock 构造数据并注入一次写入失败。原生 UI 验收通过模拟器完成真实进程重启、列表恢复和再编辑。

## 验收与交付

按 R1–R7 执行至少六条自动化测试，涵盖正常、边界、异常，并保留执行日志。原生运行路径依次为新建空间、选择构件、拖动与变换、检查冲突、命名保存、终止进程、重启、重新打开与修改。仓库保留应用、本文、README、截图和运行录屏。个人技术总结与实际开发贡献由提交人结合真实经历核对。
